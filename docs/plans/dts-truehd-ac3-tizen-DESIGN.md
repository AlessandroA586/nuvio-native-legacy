# DESIGN: DTS / TrueHD → Dolby Digital 5.1 on NuvioTpk (Samsung Tizen 8–9)

Date: 2026-10-12. Supersedes the architecture section of `dts-truehd-ac3-tizen.md`
(the fixed behaviour rules there still apply). Scope unchanged: only the full
`NuvioTpk` package, S95C on Tizen 9, HDR10/HDR10+ video untouched, Dolby Vision
out of scope.

Every claim is tagged **VERIFIED** (with the source, file:line, or host test id
from `tools/dts-tizen-lab/host_tests.py`) or **ASSUMED** (needs the TV).

## 1. Decision in one paragraph

Serve the movie to the TV's own `Tizen.Multimedia.Player` as a **loopback HLS VOD
playlist whose segments are generated on demand**: the playlist is built from the
source's keyframe index (MKV Cues / MP4 `stss`), and each segment request runs the
existing LG converter engine in a new *remux mode*: video packets copied byte for
byte, the selected DTS/TrueHD track converted to AC3 5.1 640 kb/s, muxed to MPEG-TS
with one fixed timeline. The player keeps doing what it already does well (buffering,
seeking by `SetPlayPositionAsync`, reporting absolute position and duration), so
progress bar, resume, Trakt and external subtitles need **no offset bookkeeping**.
Progressive loopback with restart-on-seek is the fallback for files without an index.
`MediaStreamSource` (public, no privilege) gets a 10-line capability probe in S0 and
is not the plan. The PC lab already proves on the host that independently generated
segments are **identical** to one continuous conversion (T5), video is bit-exact
(T1), HDR10 survives (T2), channel map and level are right (T3) and A/V offset is
within 1 ms after seeks (T4).

### 2.2 Defects the draft plan would have hit (found by the tests)

1. **MKV video has no DTS, and libnuvio has no software video decoder**, so
   `has_b_frames` is unknown and every muxer rejects the packets ("non monotonically
   increasing dts"). Fix used in `tvconv.c` (`vq_emit`): `dts[n] = min(pts[n..n+8]) −
   8·frame` with an 8-packet lookahead. It is deterministic from any keyframe, so a
   segment and a continuous run produce the same DTS (T5). The LG path never saw this
   because Starfish is fed PTS only.
2. **Per-frame timestamps must not drive trimming/padding.** MKV stores 1 ms ticks;
   TrueHD frames are 40 samples (0.83 ms), DTS frames 512. Re-syncing on every frame
   shredded the audio (wrong channel map in the FFT check, level off by 1.9 dB on DTS).
   Fix: each frame only *constrains* the offset (`[pts − tick/2, pts + tick/2] −
   counted samples`); the intersection over the warm-up frames is snapped to the codec
   frame grid and **locked**; after that the position is offset + count, and only a
   jump > 100 ms resyncs. Result: sample-exact anchors (window 10–18 samples, snapped).
3. **The first frames after a seek carry a stale timestamp** (TrueHD: 13 ms early,
   decoder hunting for a major sync). The LG engine anchors on the first frame
   (`dts_engine.c:534-538`), fine for DTS, wrong for TrueHD. Same fix as 2.
4. **The muxer shifts negative timestamps on its own** (`avoid_negative_ts`), by a
   different amount in each run, which breaks segment continuity (seen: +0.328 s in
   one run, 0 in another). Fix: `AVFMT_AVOID_NEG_TS_DISABLED` and one fixed
   `output_ts_offset` (10 s) for every run.
5. **Open GOP** (x265 default) puts leading pictures with `pts < keyframe` after the
   keyframe in decode order. Segment boundaries must be cut in **decode order** (start
   at the keyframe packet, stop at the next boundary keyframe), never by pts, or a few
   frames vanish at every boundary.
6. **FFmpeg parses MKV Cues lazily** (on the first seek). The playlist builder must
   issue one seek before reading `avformat_index_get_entry` (T5 "keyframe index").
7. **AC3 in fragmented MP4** needs `delay_moov` (the `dac3` box comes from the first
   packet).
8. **Retail Samsung TVs close `sdb shell`** (`intershell_support:disabled`; a Tizen 7
   TV-profile report on Samsung's forum, and the repo itself never used `sdb shell`,
   only `sdb dlog`). The draft's test method (`echo URL > /tmp/nuvio-video` over
   `sdb shell`) is very likely unavailable on the S95C. S0 therefore ships a small
   **probe build** with a LAN control port (§6). Check first with `sdb capability`.

### 2.3 Decoder choices (VERIFIED in FFmpeg 7.1.5 source, quality on real files ASSUMED)

* **DTS (all variants): decode the core only** (`core_only=1`, `dcadec.c:384`). The
  core is the backward-compatible 5.1 (or 2.0) mix and already carries more than AC3
  640 kb/s can: XLL lossless decoding would cost CPU for nothing. Embedded 7.1 → 5.1
  is done by the encoder that made the core. DTS:X objects are lost either way.
* **TrueHD/MLP wider than 5.1: request the encoded 5.1 presentation** (`downmix=5.1`,
  `mlpdec.c:309-323, 585-588`): the decoder reads the 6-channel substream and skips
  the 8-channel and Atmos substreams. Cheaper than full decode + matrix and it is the
  mix the studio authored. Fallback when no 6-channel substream exists: full decode +
  swresample default matrix.
* Stereo sources → AC3 2.0 192 kb/s; mono → 1.0. Output always 48 kHz.

## 3. Options compared

| | A. Progressive loopback, restart on seek (draft) | **B. Loopback HLS VOD, segments on demand** | C. Growing file on disk | D. `MediaStreamSource` packet push | E. PCM via `AudioPlayback` + muted video |
|---|---|---|---|---|---|
| Seek | Tear down + new Player + Prepare at `?t=` (1–3 s, black, new events) | Native `SetPlayPositionAsync`; player fetches the segment (T6) | Native within written part only | App flushes and re-pushes (`SeekingOccurred`) | Manual, two clocks |
| Startup | Prepare + first bytes | Playlist (from index, in memory) + first segment | Must write ahead | Push after Ready | — |
| Position / duration | Player sees an unbounded stream from the offset: app adds offset everywhere (bar, resume, Trakt, subs, skip markers) | Player reports absolute time and real duration: nothing changes in the app | Grows | App's pts | App |
| A/V sync | Muxed, ≤1 ms (T4) | Muxed, ≤1 ms; segment joins sample-exact (T5) | Muxed | Pts pushed by app | Hand-made, drifts |
| HDR10 / HDR10+ | Kept (T2) | Kept: VUI + SEI (T2); MKV container-only mastering metadata is lost in TS (rare; PQ still signalled) | Kept | Bitstream only, unknown on TV | Kept |
| Embedded subtitles | Could be muxed in MKV | Not carried: app renders them from the engine (§4.5) | — | App | App |
| Memory / CPU | 1 engine | 1 engine; 2 if the player fetches two segments at once | Disk writes of a 60 GB remux | Push from C# per packet | High |
| Unknowns | Player on an unbounded MKV/TS without Range | Player on 127.0.0.1 HLS, request pattern | Flash wear, space | Whether Samsung implements it for HEVC 10-bit 4K | Multichannel PCM over eARC |
| Verdict | **Fallback** (no index) | **Chosen** | Rejected | **Probe only** (S0) | Rejected (draft) |

Why B over A: A's seek model leaks into every feature that reads position. B keeps
the app exactly as it is for a normal URL; the only new contract is "this URL is
ours". B's extra cost (playlist from index, one generator per segment) is what T5/T6
already prove. If S0 shows the player refusing loopback HLS but accepting
progressive TS, A is implemented instead with the same engine (only the server
changes).

## 4. Architecture of B

```
Tizen.Multimedia.Player ──GET http://127.0.0.1:P/<token>/v.m3u8──▶ libnuvio loopback server (new, dts_hls_tpk.c)
        ▲                     GET .../seg<N>.ts                       │ playlist: from Cues/stss (one seek to load)
        │ (unchanged URL path:                                        │ segment N: engine remux mode
        │  Video.cs Abrir/Buscar/Faixas)                              ▼
        │                                              dts_engine (range reader, 4 lanes, unchanged)
        │                                                ├─ video packets copied (Annex-B, decode-order cut)
        └──────────── AC3 5.1 + HEVC in MPEG-TS ◀───────┤─ DTS core / TrueHD 5.1 presentation → AC3 640k
                                                         └─ subtitle packets → app subtitle path
```

### 4.1 Server (`src/dts/dts_hls_tpk.c`, new; template `src/proxyts.c` + `celular.c`)
* One session per playback, bound to `127.0.0.1`, free port, random token in the
  path, Host check. If S0 shows the player cannot reach 127.0.0.1, bind the LAN IP
  (the `celular.c` pattern) and keep the token.
* `GET /<token>/v.m3u8`: `#EXT-X-VERSION:3`, `PLAYLIST-TYPE:VOD`, `INDEPENDENT-SEGMENTS`,
  `ENDLIST`; boundaries = keyframes grouped to ≥6 s (`nvlab_server.py` `SEGS`).
  `EXTINF` = boundary deltas, last one to the container duration.
* `GET /<token>/seg<N>.ts`: chunked transfer; the generator streams while it runs.
  When N follows the previous segment, the generator **continues** instead of seeking
  (the lookahead packets are already in memory). At most 2 generators; a third
  request cancels the oldest. Cancel on close/new session.
* Fixed timeline: TS timestamps = source + 10 s (§2.2-4).

### 4.2 Engine changes (`dts_engine.c/.h`, shared with webOS)
* Accept `AV_CODEC_ID_TRUEHD`/`MLP` besides DTS; decoder options of §2.3.
* Exact anchor (§2.2-2/3) replaces `resample()`'s first-frame anchor. It also benefits
  webOS; the LG fixtures must keep passing.
* Remux mode: `dts_engine_open_range(start_kf, end_kf)` cutting in decode order,
  lookahead DTS (§2.2-1), AC3 on the global 1536-sample grid with 2 frames of
  pre-roll dropped (this is what makes T5 bit-identical), warm-up re-seek of
  `pre-roll + 0.25 s` before the keyframe.
* Keep the webOS API unchanged (`dts_engine_set_ac3`, passthrough DV path).

### 4.3 Player wiring (`src/video_tpk.c`, `tizen-tpk/Video.cs` untouched in principle)
* Decision before Prepare when the MKV header is already known (pre-fetch probe,
  `sondaMkv` → `mkvFx`): selected/preferred track is DTS/TrueHD/MLP and no
  AC3/E-AC3/AAC track in the same language → open the loopback URL directly. Else
  keep today's flow; when `avaliarAudioTv()` sets `audioNaoSup` (or the player logs
  `NotSupportedAudioCodec`), reopen on the loopback URL at the current position.
* The host sees a normal URL. `SetPlayPositionAsync`, `GetPlayPosition`, duration,
  buffering events work as for any HLS URL (ASSUMED until S0 item 3 passes).
* Audio sheet: list tracks from `mkvFx` (codec, channels, language; labels from
  `audioinfo.c`), e.g. "DTS-HD MA 7.1 → Dolby Digital 5.1". Picking another
  DTS/TrueHD track = new playlist URL at the current position; picking a native
  track = original URL at the current position.

### 4.4 Settings
Reuse `AJ_DTS_AC3` (no enum change). `dtsConversaoExiste()` → 1 on `NV_TPK` when the
engine is built; default 5.1 on this build; texts at `ajustes.c` ~5177, ~5463, ~5679,
~6954 updated in all 28 tables (`python3 tools/idiomas.py`).

### 4.5 Subtitles in converted mode
External/OpenSubtitles: unchanged (they follow player position, which stays absolute).
Embedded text tracks: the engine already demuxes subtitle packets
(`DTS_SUBTITLE`, `dts_subtitles.c`); feed text cues to the app's existing subtitle
drawing (the path `NvVid.Legenda` uses today). Embedded ASS keeps going through the
app's own `mkvass`. PGS: same RGBA path as the LG overlay or "not in v1" — owner
decision (open question 6).

### 4.6 Failure handling (rule 4 of the draft)
Generator error, no index, encrypted media, or player error on the loopback URL →
reopen the original URL at the current position, log `[dts-tpk] <reason>`, show the
existing "TV refused the audio" notice. No index → progressive TS fallback (model A)
only if S0 proves it plays; otherwise straight to the original URL.

## 5. Answers to the brief's questions

1. **Delivery without Partner privileges**: B (loopback HLS, on-demand TS segments).
   Comparison in §3; C and E rejected; D probed only.
2. **Container/muxer for HEVC/H.264 + AC3 over loopback**: MPEG-TS for HLS (HEVC in TS
   is listed by Samsung; HLS TS segments listed since Tizen 3 for the web stack).
   Muxer settings proven on host: `avoid_negative_ts` disabled, fixed +10 s offset,
   lookahead DTS, decode-order cuts, AUDs inserted by the muxer, Annex-B with
   parameter sets at keyframes (`hevc_mp4toannexb`). Fallbacks to test on the TV in
   order: progressive TS, static MKV, static MP4 (all served by the lab).
3. **Static FFmpeg for the .tpk**: the configure line in `tools/dts-tizen-lab/build.sh`
   (decoders `dca,truehd,mlp` + LG's subtitle decoders; encoders `aac,ac3`; demuxers
   `matroska,mov`; muxer `mpegts` (+`matroska,mp4` only if model A needs them);
   parsers `dca,mlp,h264,hevc,aac,ac3`; bsfs `h264/hevc_mp4toannexb,dca_core,truehd_core`;
   swresample). ≈2.7 MB stripped on x86-64; ARM size in S1. LGPL 2.1 static inside a
   GPLv3 app whose full source is public: ship `COPYING.LGPLv2.1` + `SOURCE.txt` in
   `res/licencas/dts/` as the LG package does (not legal advice; owner decides).
4. **Seek model**: HLS native seek; position/duration absolute from the player, so
   progress bar, resume (open + seek, as today), Trakt scrobble and subtitles keep
   working unchanged. Model A would need an offset everywhere (why it is the fallback).
5. **Audio-track UX**: list from the MKV header the app already reads (`mkvFx`),
   label "<codec> <channels> → Dolby Digital 5.1", prefer a native AC3/E-AC3/AAC track
   in the preferred language (no conversion), switch = new URL at current position.
6. **Risks and cheapest experiments**: §8, ordered by cost; most are retired by the
   S0 probe build + lab server before any feature code.
